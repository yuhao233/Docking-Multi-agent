**幻灯片 6 — 受体三态纪律（产品底线，代码强制）**
- 没提受体 → **`decision=ask`、零对接计算**：只提问（① PDB 编号 / UniProt accession；② 受体名称，中英文，在线解析；③ 上传结构文件），**系统没有默认受体**，不提供预置受体候选、不写「已使用系统默认…」。
- 点名可解析 → **第一步自动解析**（UniProt 多策略 + RCSB/AlphaFold），报告写明 accession/物种/结构来源。
- 点名不可解析或歧义 → 列 `choices` 让用户选，**零对接计算**；代码护栏在任何引擎调用前拦下（`agents/dispatch.py:315`）。
- 实测：拟南芥 ROS1 → Q9SJQ6/7YHP 自动继续；只写「ROS1」→ 7 个候选并列 64.0 → 停下让用户选（`var/e2e/final_ambig.sse`）。

**幻灯片 7 — 对接盒：工具定盒 + 一致性第一**
- 来源优先级：显式指定 > 实验位点 > 工具预测（P2Rank/几何法）> 质心兜底（`core/pockets.py:867`）。

**幻灯片 8 — 对接参数自动规划：精度优先 + 预算护栏**

## 1. 项目概述

### 1.1 要解决的问题

**结论：本系统解决的是「把一个小分子库在一个已知/可推断的结合位点上跑完真实对接，并给出可复算、可追溯的排序与报告」。**

| 痛点 | 现状做法 | 本系统做法 |
|:---|:---|:---|
| 受体准备繁琐 | 手工去水、加氢、转 PDBQT、猜盒子坐标 | 上传 `.pdb` 即现场用 meeko 准备，盒子由口袋工具确定（`core/receptors.py:235`、`core/pockets.py:867`） |
| 盒子放错位置 | 直接对整个蛋白质求质心 | 优先级链 + 工具预测验证；apo 受体自动改用 P2Rank top-1（`README.md §11.2b`） |
| 大库跑不完 | 全库高搜索强度硬跑 | 两阶段漏斗 + pilot 预算护栏 + 并发规划（`core/params.py:372`、`core/docking.py:86`） |
| 结果不可信 | 模型自己编数字 | 数值只来自 RDKit / Vina / P2Rank 工具返回；`verify_docking.py` 独立复算取证 |
| 特殊化学被静默丢弃 | 直接丢掉全部 HETATM、把盐丢给 Vina | 逐条上报 `dropped_hetatm`/`kept_hetatm`/`unsupported_hetatm`，配体拆分给 `dock_smiles`+`removed_fragments`（`docs/api.md §16`） |
| 意图含混时行为摇摆 | 提示词里两条规则互相冲突 | 受理层显式给 `decision`，编排层只执行（`docs/architecture.md §4.1`） |

### 1.2 六条能力目标与验收标准

来源：`docs/architecture.md §1.1`（原表照录）。

| # | 能力 | 验收标准（可观测） | 现状落点 |
|:---|:---|:---|:---|
| G1 | 自动准备 | 用户只给 PDB/小分子文件即可开跑；盒子由工具确定而非臆造 | `core/receptors.py`、`core/ligands.py`、`core/pockets.py` |
| G2 | 自动对接 | 全部候选分子都有真实引擎返回的能量；大库能在有限算力内跑完 | `core/docking.py`、`agents/coordinator` 漏斗纪律 |
| G3 | 自动评估 | 物化性质/类药性/结合模式与对照比较，全部来自工具真实计算 | `core/chemistry.py`、`tools/{properties,binding}.py` |
| G4 | 自动异常处理 | 单分子失败不拖垮整批；失败有原因；特殊体系有事实披露与补救建议 | `runtime/errors.py`、`core/docking.py` 的 note/降级路径 |
| G5 | 总结与报告 | 固定 9 章报告 + 机器可读产物（CSV/JSON/图/位姿），数值可回溯到工具输出 | `reporting/`、`agents/persistence.py`、`runs.py` |
| G6 | 主管协调 | 受理判定 run/ask/reject；分发、并行、漏斗、分片由主管决定；流程不中断 | `intake.py`、`agents/coordinator.py`、`agents/dispatch.py` |

### 1.3 明确的非目标

来源：`docs/architecture.md §1.2`。

- **不做**分子生成 / 骨架跃迁 / QSAR 建模：本系统是「筛选与评估」而非「设计」。
- **不做**分布式集群调度：目标是**单机多进程**把多核吃满，不引入 Redis/Celery/K8s。
- **不做**自研对接引擎 / 打分函数：只做 AutoDock Vina / AutoDock4 的**编排与取证**。
- **不做**多用户 SaaS：默认只听 `127.0.0.1`，无鉴权（`config.py` 与 `web/app.js` 均按本机单用户假设）。
- **不引入**向量库 / RAG：任务输入是结构化的分子与受体，不需要语义检索。

### 1.4 两条贯穿全局的硬约束

| 约束 | 含义 | 代码落点举例 |
|:---|:---|:---|
| **真实性** | 任何数值都必须来自工具真实返回；工具失败要如实报错，禁止编造、禁止「看起来跑通了」的假成功 | `verify_docking.py` 有专门的反证用例（非法 SMILES 必须不出数值） |
| **不静默** | 任何被丢弃/改写/降级的东西都必须在结果里逐条可见，并给出补救路径 | `dropped_hetatm` / `removed_fragments` / `unsupported_hetatm`（`docs/api.md §16`） |

## 2. 总体架构

**结论：分层单向向下，受理与编排分离，两条执行路径共用同一套计算核心与报告模板。**

### 2.1 分层图

来源：`docs/architecture.md §2.1`（原图照录）。

```
入口层    cli.py / __main__.py（--check、pipeline、agent、runs、serve）
          api/app.py（FastAPI，HTTP + SSE，31 个路由）+ api/schemas.py（pydantic 校验）
受理层    intake.py（用户指令 + 表单 → 结构化 task_spec；decision ∈ run/ask/reject）
编排层    agents/coordinator.py（主管 Agent，LangGraph create_agent）
          agents/dispatch.py（发给子 Agent 的分发工具）+ pipeline.py（确定性流水线，零 LLM）
角色层    agents/workers.py（property / pocket / docking / binding，各自独立模型实例与 checkpointer）
          agents/prompts.py（子 Agent 系统提示词）
工具层    tools/{docking,properties,binding,pockets,report,online,choices}.py（@tool 共 20 个，模型唯一动作面）
核心计算  core/{docking,receptors,ligands,pockets,chemistry,ranking,params,resolve,files}.py（不依赖 LLM）
状态持久化 runtime/blackboard.py（运行内共享黑板）· runtime/tool_io.py（原始返回落盘 + 模型摘要视图）
          agents/persistence.py（唯一结果合并/落盘入口）· runs.py（运行目录、产物、分页、zip）
报告层    reporting/{report,charts,tables,content,pdf,artifacts,store}.py
运行时    runtime/{llm,streaming,errors,checkpoints,context,payload}.py
          settings.py（界面设置）· config.py（环境变量）· paths.py · cancellation.py · logging_setup.py
```

**依赖方向单向向下**：`api/cli → intake/coordinator/pipeline → tools → core`。
`core/*` **绝不** import `tools/*`、`agents/*`、`api/*`（唯一例外是 `core/receptors.py` 在函数内延迟导入
`core/pockets.py` 以避免循环依赖，`docs/architecture.md §2.1`）。实测模块行数分布见封面信息表。

### 2.2 一次运行的端到端数据流（含 SSE 事件）

来源：`docs/architecture.md §2.2`，SSE 事件类型取自 `docs/api.md §2/§7.3/§15`。

```
用户/前端  POST /api/agent/stream（或 /api/pipeline/stream）
  ▼ api/app.py 建 Run（runs.py：运行目录 + run.json）
  ├─ intake.build_task_spec(req)          确定性规则（零模型）
  │    └ 需要时 intake.refine_task_spec()  仅「对话模式 + 自然语言」调用一次 LLM
  │      decision=ask/reject → 直接回复，不调用任何工具（省算力、防胡说）
  ▼ coordinator（主管 Agent，LangGraph）
  │  提示词注入 task_spec 只读摘要（intake.render_agent_message）
  │  同一轮多个分发工具调用 → ToolNode 并发执行 → 实测并行
  ├─ agents/dispatch.py: import_molecule_library / run_property_assessment /
  │    run_pocket_analysis / run_docking / run_binding_mode_analysis
  ▼ @tool（tools/*.py）：大结果 tool_io.record() 全量落盘 + 只回 summary/top；
  │                    横向协作写 runtime/blackboard.py
  ▼ core/*（真实计算）：RDKit 构象、meeko PDBQT、Vina 对接、P2Rank/几何法口袋、排序
  ▼ agents/persistence.py（唯一落盘入口；_PROVENANCE_KEYS 回填模型漏掉的字段）
  ▼ runs.py 产物：molecules/properties/docking/binding/pockets/result.json + ranking.csv
                + report.md（固定 9 章）+ report.pdf + charts/*.png + poses/*
  ▼ SSE（runtime/streaming.py，每个事件带 ts）→ 前端 web/app.js 渲染卡片/表格/编排时间轴
```

**SSE 事件类型**（`docs/api.md §2`、`runtime/streaming.py`）：
`start` / `progress` / `stage` / `molecules` / `molecule`（小库单条）/ `token` / `thinking` /
`tool_call` / `tool_result` / `update` / `choices` / `final` / `done` / `error` / `cancelled`。
其中 `thinking` 承载模型推理（`reasoning_content`、Responses 风格 `summary`、`<thinking>` 标签、
content blocks 的 `thinking`/`reasoning` 块），经 `reasoning_of()` / `split_thinking()` 从正文里抽出后
**单独下发**（走 `custom` 帧，不混进 `messages/partial`），两套界面都把它折叠成气泡内默认收起的
「思考 · N 字」块 —— 正文只留结论，避免推理刷屏；助手回执与报告块则**全文直接显示**
（不再按行数/字数默认折叠）。
其中 `stage ∈ import | properties | pocket | docking | binding | report | done`（`docs/api.md §10.4`）。
所有事件都带服务端毫秒时间戳 `ts`（`docs/api.md §15.1`），前端据此计算每个节点的**真实起止时间**。

**实测并行样例**（`docs/api.md §15.2`，真实运行 `chat+advanced`）：

## 3. Agent 体系

**结论：6 个角色各持独立模型实例；主管只编排不计算；子 Agent 通过共享黑板横向协作；分发层有代码级边界校验与受体护栏。**

### 3.1 六个角色与工具清单

`import_molecule_library`、`run_property_assessment`、`run_pocket_analysis`、

`customize_report`、`analyze_pose_pocket`、`generate_screening_report`、`fetch_protein_structure`、
`fetch_molecule_record`。
（`list_known_receptors` 已从协调 Agent 工具面移除 —— 13 → 12；它现在是**内部/诊断**工具，
**没有任何 Agent 绑定**。`available_receptors` 已删除。）

全部 `@tool` 共 **23 个**（实测：`tools/` 下 `@tool` 装饰器计数）：
`dispatch.py` 6、`pockets.py` 4、`binding.py` 3、`properties.py` 2、`docking.py` 2、`online.py` 2、
`report.py` 1、`recommend.py` 2、`pose.py` 1。
**每个 `@tool` 的 docstring 就是给模型的说明书，因此 docstring 是接口契约的一部分**（`docs/architecture.md §3.4`）。

> **条件纪律段（`agents/prompt_blocks.py`）**：系统提示词在**每次模型调用**上重发，
> 而「执行纪律」占 `sp` 全文 55%，单次运行通常只用得到其中几条。因此 `sp` 用
> `<!-- block:KEY -->` 标记出四段 —— 上传处理 / 受体纪律 3c / 两阶段漏斗 / 特殊体系 ——
> 协调 Agent 的 `dynamic_prompt` 中间件按本次运行事实**抽掉**不相关的段
> （事实来自 `task_spec`、`param_plan` 与 `runtime/run_facts.py` 记的对接观测）。
> 安全方向写死：**没有标记 → 全文**、**事实未知 → 注入**、**组装异常 → 全文**。
> 实测常见小库运行每次调用省 ≈2,549 tokens。提示词因此不再是常量，
> 故每次注入清单随 `result.prompt_blocks` 落盘，可复盘「这次到底给了模型哪些纪律」。

> **为什么 intake 与 coordinator 分开**：早期把「受理」和「执行」写在一个提示词里，
> 「含糊就先问用户」与「分子非空就必须跑完」直接冲突，模型两头不讨好
> （`docs/architecture.md §4.1`）。现在 `decision` 由受理层显式给出，编排层只执行。

### 3.2 分发链路与边界校验

来源：`docs/architecture.md §4.2`、`agents/dispatch.py`。

```
coordinator ──(dispatch.@tool)──▶ invoke_worker(子 Agent, thread_id=角色名)
                                      │
                                      ├─ 子 Agent 调自己的 @tool（真实计算）
                                      ├─ @tool 写 blackboard（横向共享）
                                      └─ 返回 JSON 原文（经 _invoke_checked 校验关键字段）
```

| 机制 | 实现 | 位置 |
|:---|:---|:---|
| **每角色独立 LLM 实例** | `build_chat_llm(ctx, role=...)` 每次都新建 `ChatOpenAI` 并登记 `instance_id` | `agents/workers.py:48`、`runtime/llm.py:387` |
| **每子 Agent 独立 checkpointer** | `_checkpointer(role)` 懒创建一个独立 `MemorySaver` | `agents/workers.py:63` |
| **子 Agent 无状态** | 每次调用用 `f"{thread_id}-{id(agent)}-{uuid4[:8]}"` 作新 `thread_id` | `agents/workers.py:159` |
| **必需字段校验** | property→`assessment`；pocket→`pockets`；docking→`receptors` 或 `summary`（任一即可）；binding→`results` | `agents/dispatch.py:93-100` |
| **失败重试** | 带纠正提示**自动重试一次**（共 2 次尝试），纠正串在 `dispatch.py:102` | `agents/dispatch.py:121-122` |
| **两次都失败的返回** | `{"status":"agent_output_invalid","role":...,"required_keys":[...],"raw":<末尾 800 字符>}`，**不把垃圾文本喂给主管** | `agents/dispatch.py:137` |
| **同一轮多个分发调用** | LangGraph `ToolNode` 并发执行 → 界面「实测并行」的来源 | `docs/architecture.md §4.2` |
| **分片护栏** | 片数上限 `AGENT_SHARD_MAX`（默认 8），防止 LLM 往返开销反超对接本身 | `runtime/tool_io.py:147` |

**代码级护栏（不靠模型自觉）**：

| 护栏 | 触发条件 | 行为 | 位置 |
|:---|:---|:---|:---|
| 受体未指定/未解析护栏 | `task_spec.receptor.source ∈ {"unresolved","default"}` | 在**调用任何子 Agent / 对接引擎之前**返回 `{"status":"needs_user_input", ...}`，并明确禁止改用任何默认受体 | `agents/dispatch.py::unresolved_receptor_message`（`run_docking` / `run_pocket_analysis` 均先调） |

### 3.4 主管纪律条款摘要（`config/agent_llm_config.json` 的 `sp`，共 12 条）

来源：`config/agent_llm_config.json:28`（实测 `sp` 长 8,162 字符）。

| 条目 | 要点 | 为什么 |
|:---|:---|:---|
| 1 | `decision=run` 时只要分子库非空就必须**完整执行**（导入→属性→对接→结合模式→报告），不得中途询问 | 产品底线 |
| 2 | 阳性对照是**可选项**：只有明确给了 SMILES 才做对照对接与结合模式比较 | 修复「阳性对照总是使用默认值」 |

| 5 | 最终必须调用 `generate_screening_report` 出报告 | 产物完整性 |
| 6 | 某一步失败要如实报告原因并继续其余可执行步骤 | 失败可见 |
| 7 / 9 | 有阳性对照时必须对对照也对接；对照对接由工具自动补入，不必单独再调 | 基线完整性 |

| 10 / 11 | **大库纪律**：≥500 走两阶段漏斗（全库粗筛 exh=1 → 头部精算 `top_from_previous=200, exh=16`）；子 Agent 工具一律留空分子参数；不按固定分子数切成很多片；分片不超过 `AGENT_SHARD_MAX`（8） | 算力最优 + 防上下文爆炸 |

## 4. 任务受理层（intake）

**结论：受理层是纯确定性规则（零网络、零模型即可跑），只在「对话模式 + 自然语言」时额外调用一次受理模型；
它输出三态决策与结构化规约，编排层只读。**

### 4.1 调用链

来源：`docs/api.md §14.1`。

```
POST /api/agent/stream
  → resolve 计数清零
  → thread_id = conversation_id or run_id
  → graph.aget_state(thread)              读最近 8 条 human/ai 作为 prior_turns（只读）
  → intake.build_task_spec(req, prior_turns=...)  确定性规则（零模型；继承上一轮分子/受体）
  → [需要时] intake.refine_task_spec()   受理模型（角色 intake，温度 0；上下文里带 prior_turns）
  → intake.render_agent_message(spec)    渲染成协调 Agent 的消息
  → run.data["task_spec"] = spec         写入运行记录（可观测）
  → graph.astream(..., config={"configurable":{"thread_id": thread_id}})  协调 Agent 按规约编排
```

### 4.2 确定性规约字段（`task_spec`）

来源：`intake.py:478-501`、`docs/api.md §14.2`。

| 字段 | 取值 | 说明 |
|:---|:---|:---|
| `task_type` | `screening` / `properties_only` / `docking_only` / `binding_only` / `report_only` / `unknown` | `TASK_TYPES`（`intake.py:49`），由 `_guess_task_type` 从指令关键词判定（`intake.py:99`） |
| `goal` / `authority` | 用户目标或 `DEFAULT_AGENT_TASK`（`intake.py:45`）/ `manual`·`chat`·`chat+advanced` | authority 由 `mode` + `advanced` 决定（`intake.py:347`） |

### 4.3 run / ask / reject 判定规则

来源：`intake.py:510`（`_can_ask`）、`intake.py:535`（`_finalize`）。

| decision | 成立条件 | 编排层行为 |
|:---|:---|:---|
| `reject` | `out_of_scope == True`（受理模型判定闲聊/无关） | 友好说明能力范围，**不调用任何工具** |
| `ask` | ① `receptor.source ∈ {"unresolved","default"}`（点名未解析 / 未指定受体，**优先于多轮守卫**；系统没有默认受体）；或 ② 规约里没有任何可识别分子来源且未明确同意用示例库（含上一轮继承） | 只说明缺什么并提问，**不调用任何工具** |
| `run` | 其余全部情况（受体与分子库都已指定） | **必须完整跑完**；唯一例外是 `receptor.source == "named"` —— 必须先自动解析 |

**关键设计：必需信息不齐 → 只提问、零计算**。受体与分子库是必需项（未指定受体 / 点名未解析 / 无分子来源
都判 `ask`），系统**没有默认受体**，分子也不会静默用示例库；对照与对接参数仍有默认值，位点由口袋工具确定。
这条规则来自实测：`scripts/intake_eval.py --live` 曾抓到受理模型把 5 个本该 `run` 的用例判成 `ask`
（`README.md §1`「任务受理层与编排层的分工」注）；现在反过来——必需项缺失必须 `ask`，回归用例两侧都看护。
受理模型置的 `needs_user_input` **不会**覆盖一个已完整指定（受体+分子库）的规约。

### 4.4 分子抽取（三种写法）

来源：`core/ligands.py:52`（`extract_smiles`）、`intake.py:289`、`docs/api.md §14.3b`。

| 写法 | 示例 | 处理 |
|:---|:---|:---|
| `名称:SMILES` | `阿司匹林:CC(=O)Oc1ccccc1C(=O)O` | 直接切分（`core/ligands.py:37` `_split_candidates`） |
| `名称 空格 SMILES` | `华法林 CC(=O)CC(c1ccccc1)c1c(O)c2ccccc2oc1=O` | 按「含空白」的词法切分并回填名称 |
| 散文中夹带的分子 | 「帮我筛一下：咖啡因 Cn1cnc2c1c(=O)n(C)c(=O)n2C」 | 抽取 SMILES 片段，散文被忽略 |

受理顺序（`intake.py:373-395`）：表单文本 → 上传/路径文件 → **指令中确定性抽取**（`source="message"`）
→ 上一轮继承（`inherited="prior_turns"`）→ 最后才轮到示例库（`source="library"`，**仅在用户明确要求用时**才真正加载）。
**「用户写了分子却对接了示例库」是真实发生过的缺陷**：旧分词只按 `,;\n` 切分，
「名称 空格 SMILES」整句被当成一个 SMILES 解析失败 → 静默退回内置示例库，
用户看到的是别人的分子被对接打分（`CHANGELOG.md` 第 24 条）。现已有回归用例看护。

### 4.5 多轮会话（`conversation_id`、`prior_turns`、`_can_ask` 例外）

来源：`docs/api.md §2`「多轮会话」、`intake.py:303`、`intake.py:320`、`intake.py:510`。

### 4.6 受体三态纪律（核心）

来源：`intake.py:397-453`、`intake.py:978`（`docs/api.md §14.1b`）、`config/agent_llm_config.json` 第 3c 条。

| 情形 | `receptor.source` | 判定 | 系统行为 |
|:---|:---|:---|:---|
| 完全没提受体 | `default` | `ask` | **零对接计算**：只提问并给出三条出路（① PDB 编号 / UniProt accession；② 受体基因/蛋白名（中英文，在线解析）；③ 上传受体结构文件）。提问文案里不给示例编号（助手回复中的示例编号曾被下一轮误当成用户指定）。**系统没有默认受体**（`DEFAULT_RECEPTOR_NAME` 已删除），不给预置受体候选 |
| PDB 号 / UniProt accession / 受体名称 / 上传受体文件 | `user` | `run` | 按用户指定的受体执行 |
| 点名了具体受体，但字面不是 PDB/accession（如「植物去甲基化酶ROS1」「EGFR」） | `named` | `run` | **第一步调用 `fetch_protein_structure` 自动解析**；高置信唯一候选 → 继续完整流程，报告写明 accession/物种/蛋白名/结构来源/打分依据 |
| 检索到多个同样合理的候选，或单一候选置信度不足 | `unresolved`（工具写回） | `ask` | **零对接计算**：把候选列成 `choices`（accession / 物种 / 蛋白名 / 结构来源 / 打分），用户点选后以同一 `conversation_id` 继续 |
| 一个都没查到 | `unresolved`（工具写回） | `ask` | **零对接计算**：提问并**逐条列出已尝试的检索**，请用户提供 PDB ID / accession / 文件 |

**代码级兜底**：`unresolved_receptor_message(run)` 会在任何子 Agent / 引擎工作**之前**拦下
`receptor.source == "unresolved"`（返回 `{"status":"needs_user_input","attempts":[...],"candidates":[...],"message":"..."}`）
与 `receptor.source == "default"`（返回 `{"status":"needs_user_input","missing":["receptor"],...}`，不给任何预置受体候选）
两种情形，`run_docking` / `run_pocket_analysis` 都会先调它 —— 即使主管 Agent 没照提示停下来问，
也**绝不可能**用默认受体把结果算出来。写回动作由 `tools/choices.py::mark_receptor_unresolved` 完成（`tools/choices.py:29`）。

**实测对照**（`var/e2e/evidence_resolve.out`、`var/e2e/final_ambig.sse`）：

| 输入 | 解析状态 | 结果 |
|:---|:---|:---|
| 「植物去甲基化酶ROS1」（含物种线索） | `resolved` | Q9SJQ6 / Arabidopsis thaliana / DNA glycosylase-AP lyase ROS1 / 打分 114.0 → 自动继续 |
| 只写「ROS1」（无物种线索） | `ambiguous` | 7 个候选并列 64.0（人源激酶 P08922、小鼠 Q78DX7、大鼠 Q63132、拟南芥 Q9SJQ6…）→ **零对接**，下发 4+ 个 `choices` |
| 「不存在的蛋白ZZZQQ9」 | `not_found` | **零对接**，回执逐条列出 3 次已尝试检索，并给出三条出路 |

**结论：名称归一化 → 物种线索 → UniProt 多策略检索 + 规则打分 → 三态判定 → RCSB/AlphaFold 结构获取 + 全字段溯源；
所有「不确定」都变成结构化 `choices` 交回用户。**

### 5.1 名称归一化与中英映射

来源：`core/resolve.py:179`（`normalize_molecule_name`）、`core/resolve.py:189`（`extract_gene_tokens`）、
`core/resolve.py:212`（`map_family_terms`）、`core/resolve.py:228`（`normalize_query`）。

|:---|:---|:---|
| 基因 token 抽取 | 从「植物去甲基化酶ROS1」抽出 `ROS1` | `extract_gene_tokens`（`core/resolve.py:189`） |

### 5.2 UniProt 多策略检索

来源：`core/resolve.py:447`（`build_uniprot_queries`）、`docs/api.md §14.1c`。

按精度从高到低依次构造检索式（去重后依序尝试）：

| 顺序 | 策略名 | 检索式 |
|:---|:---|:---|
| 0 | `accession` | 直接 accession / entry ID 直查（有则最高优先） |
| 1 | `gene+species` | `gene_exact:<GENE> AND organism_id:<taxid>` |
| 2 | `gene+reviewed` | `gene_exact:<GENE> AND reviewed:true` |
| 3 | `gene` | `gene_exact:<GENE>` |
| 4 | `family+species` | `(<家族词>) AND (organism_id:<taxid>)` |
| 5 | `family+plant` | `(<家族词>) AND (plant OR Arabidopsis)` |
| 6 | `free-text` | 英文自由文本（基因 + 家族词 + 物种名） |

> 泛化家族词（`protein` / `enzyme` / `receptor` / `channel`）**不用于构造检索式**：
> `(receptor) AND reviewed:true` 会命中成百上千条（`core/resolve.py:160-162` `GENERIC_FAMILY_TERMS`）。

### 5.3 打分规则（逐条列出）

来源：`core/resolve.py:338`（`score_candidate`）与模块 docstring（`core/resolve.py:16-27`）。

| 项 | 分值 | 说明 |
|:---|:---|:---|
| Swiss-Prot 已审阅 | **+40** | 人工审阅条目优先于 TrEMBL |
| 物种精确匹配 | **+30** | 候选 taxid == 线索 taxid（如拟南芥 3702） |
| 同为植物 | **+18** | 线索是植物但候选是另一种植物 |
| 物种不符 | **−25** | 线索是植物却命中人源/鼠源等 |
| 蛋白名含映射家族词 | **+20** | 如 demethylase / DNA glycosylase / kinase |
| 蛋白名不含家族词 | **−10** | 只在用户给了家族词时扣 |
| 基因名精确匹配 | **+15** | `gene_names` 里逐字等于线索基因（`ROS1 ≠ ROS1A`） |
| 注释完整度 | **+3×3** | 蛋白名 / 基因名 / 物种三项各 +3 |

**三态判定阈值与状态**（`core/resolve.py:60-63`、`decide_status` `core/resolve.py:378`）：

| 常量 | 值 | 作用 |
|:---|:---|:---|
| `MIN_ACCEPT_SCORE` | 25.0 | 最高分低于此 → `not_found` |
| `AMBIGUITY_MIN_SCORE` / `AMBIGUITY_MARGIN` | 45.0 / 8.0 | 次高分 ≥ 最高分 − 8 且 `best ≥ 45` **且**两者物种不同 → `ambiguous` |
| `LOW_CONFIDENCE_SCORE` | 55.0 | 单一候选低于此 → `low_confidence`；另要求已审阅、物种匹配、基因精确、家族词匹配 |

| 状态 | 含义 | 上层行为 |
|:---|:---|:---|
| `resolved` | 唯一候选且所有用户给出的线索都强匹配（精确 accession 本身即权威，不再推断） | 自动继续 |
| `ambiguous` | 多个分数接近、跨物种无法消歧 | 列候选让用户选 |
| `low_confidence` | 单一候选但置信度不足（未 reviewed / 物种不符 / 名称只部分匹配） | 列出让用户确认 |
| `not_found` | 一个都没查到 | 逐条列出已尝试检索 |

### 5.4 RCSB → AlphaFold 结构获取链与溯源字段

来源：`tools/online.py:324`（`fetch_protein_structure`）、`docs/api.md §14.1c`。

```
名称（含中文）→ normalize_query（基因 token / 物种线索 / 中文家族词→英文）
  → 多策略检索 UniProt（§5.2）→ 打分（§5.3）→ 三态判定
  → 结构链：UniProt PDB 交叉引用 / RCSB Search 反查的实验结构优先；
            没有实验结构、或候选结构都准备失败 → AlphaFold DB（用接口返回的 pdbUrl，模型版本不写死）
  → prepare_user_receptor 生成 PDBQT（含 altloc 重试与内容哈希缓存）
  → 溯源：accession / entry_id / 物种 / 蛋白名 / structure_source(rcsb|alphafold) / structure_url /
          下载文件与大小 / AlphaFold 模型版本 / 打分理由 / 已尝试检索
```

**返回 JSON 关键字段**（成功路径，`docs/api.md §14.1c`）：
`receptor_file`、`box_center`、`box_size`、`structure_source`、`pdb_id`（RCSB）或 `alphafold`（预测模型）、
`accession`、`organism`、`protein`、`score`、`score_reasons`、`why_selected`、`structure_url`、
`structure_file`、`file_size`、`receptor_resolution.attempt_summary`、`candidates`、`provenance`。

**候选结构准备失败会自动换下一个候选**（`README.md §9`），并在 `attempts` 里留痕。

**实测（`var/e2e/evidence_resolve.out`）**：`植物去甲基化酶ROS1` 的 6 条检索依次命中 1 / 7 / 8 / 8 / 8 / 8 条，
最终选中 Q9SJQ6（打分 114.0 = 40 + 30 + 20 + 15 + 9），`pdb_ids` 为 `7YHO / 7YHP / 7YHQ`；
只写 `ROS1` 时前三条检索分别命中 7 / 8 / 8 条，7 个候选同为 64.0 → `ambiguous`。

### 5.5 `choices` 结构化选项协议

来源：`tools/choices.py:1-16`、`docs/api.md §7.3`、`intake.py:146`。

**选项结构**：`{id, kind, label, value, prompt, detail}`，`kind ∈ receptor | molecule`。

| 字段 | 含义 |
|:---|:---|
| `id` | 稳定标识，如 `receptor:Q9SJQ6` / `molecule:3034368:organic` |
| `kind` | 受体或分子 |
| `label` | 给人看的完整描述（accession / 物种 / 蛋白名 / 结构来源 / 打分） |
| `value` | 机器可用值（accession / CID / SMILES） |
| `prompt` | 点选后**原样发出**的下一轮追问 |
| `detail` | 结构化细节（物种、蛋白名、结构来源、pdb_ids、打分、理由） |

- 下发通道：SSE `choices` 事件 + `run.data.choices` + `GET /api/runs/{id}` 的 `run.choices`，
  同一次运行只发一次（心跳路径与 `final` 前各有一条触发路径，已去重，`docs/api.md §7.3`）。
- 前端渲染成助手气泡下方的可点按钮；点选后以**同一 `conversation_id`** 发送 `prompt`。
- 高置信解析成功时**不会**出现 `choices`（直接继续，不打扰用户）。
- 陈旧清理：`clear_choices(kind)` 只清**同类型**的旧候选项 —— 同一运行里「分子是混合物要选、受体已高置信解析」是正常组合
  （`tools/choices.py:92`）。

**分子多组分/混合物的处理（以 Mancozeb 为例）**：`fetch_molecule_record` 命中多组分/配位聚合物时
**不臆造单一结构**（`tools/choices.py:146` `mixture_choices`），返回原始 SMILES、`is_mixture`、
`components`、`representative_smiles` 与 `mixture_note`，并给出 4 个选项：

| 选项 | 取法 | 值（实测，`var/e2e/final_turn1.sse`） |
|:---|:---|:---|
| ① 原始多组分 | PubChem 原始多组分结构，金属与配体片段原样保留 | `C(CNC(=S)[S-])NC(=S)[S-].C(CNC(=S)[S-])NC(=S)[S-].[Mn+2].[Zn+2]` |
| ② Zn-EBDC 单体 | 金属 + 最大有机片段 | `S=C([S-])NCCNC(=S)[S-].[Zn+2]` |
| ③ Mn-EBDC 单体 | 金属 + 最大有机片段 | `S=C([S-])NCCNC(=S)[S-].[Mn+2]` |
| ④ 最大有机片段 EBDC | 无金属代表结构 | `S=C([S-])NCCNC(=S)[S-]` |

- 正确 CID 与分子式：**PubChem CID 3034368 / C₈H₁₂MnN₄S₈Zn**（`var/e2e/final_turn1.sse` 的 `choices[0].detail`）。
- 每个选项的 `detail.note` 都如实提示「对接引擎通常不支持金属配位，实际分数需谨慎解读」。
- 中文别名映射：代森猛锌 / 代森锰锌 → Mancozeb（`README.md §9`）。

## 6. 受体与配体准备

**结论：受体准备去水去杂原子但**逐条溯源**，`keep_hetatm` 可要求保留并按**最终 PDBQT 内容**回填；
配体准备用 ETKDGv3 + MMFF 生成 3D 构象，并在对接前做一次确定性「化学体检」。**

### 6.1 受体准备：去水 / 杂原子溯源

来源：`core/receptors.py:178`（`_write_prep_pdb`）、`core/receptors.py:235`（`prepare_user_receptor`）、
`docs/api.md §16.1`。

| 字段 | 含义 | 实测样例 |
|:---|:---|:---|
| `dropped_hetatm` / `dropped_waters` | 按标准流程剔除的非水杂原子计数（残基名 → 数量）/ 剔除的水分子数 | `{"5CM": 20}`、`{"HEM": 43, "SO4": 10}` / `0` |
| `kept_hetatm` | **最终受体 PDBQT 里实际存在**的白名单残基计数（以文件内容为准，不是「打算保留」） | `{"SF4": 8}` |
| `unsupported_hetatm` / `cocrystal_ligand` | 要求保留但因缺少 meeko 模板未能进入受体的残基 / 用于定位位点盒的共晶配体（`resname`/`n_atoms`/`center`） | `[]` 或 `["HEM"]` / `5CM` |

- **实测（本次运行）**：受体 7YHP 的 `dropped_hetatm = {"5CM": 20}`、`kept_hetatm = {"SF4": 8}`、
  `unsupported_hetatm = []`（`var/runs/20260915-174954-6983/docking.json`）；
  对应的 note 为「受体 7YHP 丢弃了非水杂原子：5CM×20（水 0 个）…」（`var/runs/20260915-174954-6983/run.json` 的 `notes`）。
- **实测（金属离子 vs 大辅因子）**：`ZN/MG/CA/FE/MN/CL` 等金属离子可直接保留；
  `HEM`、`NAD`、`GOL` 等有机残基需要 meeko 模板，否则计入 `unsupported_hetatm`（`docs/api.md §16.1`）。
- **保留失败不会崩**：实现会**逐个剔除**无法参数化的残基直到准备成功，
  把剔除名单放进 `unsupported_hetatm`，并给出三条补救路径（去掉 `keep_hetatm` 重跑 / 提供模板 SDF / 直接给已备好的 PDBQT）
  （`core/receptors.py:291-325`）。
- **`kept_hetatm` 以最终 PDBQT 内容为准**：`core/receptors.py:338` 明确「绝不出现『说保留了、其实没进对接』的假信息」。
- **共晶配体识别**：按 `(链:残基号:残基名)` 取**最大的一团非水 HETATM**，并排除离子与结晶添加剂
  （SO4/GOL/EDO/PEG…）（`core/pockets.py:345` `cocrystal_ligand`）。位点来源会写清是哪个配体，如「共晶配体(MIT)质心」。

### 6.2 `keep_hetatm` 与「已准备好的 PDBQT」

来源：`core/receptors.py:537`（`_pdbqt_spec`）、`README.md §11.4c`。

| 场景 | 行为 |
|:---|:---|
| 受体是 `.pdb` | 现场用 meeko `mk_prepare_receptor.py` 准备（`core/receptors.py:206`） |
| 受体是 `.pdbqt`，未请求保留杂原子 | 直接使用该 PDBQT |
| 受体是 `.pdbqt`，**请求了** `keep_hetatm` | 回到 `.site.json` sidecar 记录的**来源 PDB** 重新准备（`core/receptors.py:552-562`） |
| `.pdbqt` 且无来源 PDB | 无法谈保留，如实说明（杂原子在上传准备时已被剔除） |

> **实测**：1A6M 上传的 PDBQT + `keep_hetatm="OXY"` 的分数从 **−6.97 变为 −7.15**，OXY 真的进入了受体（`README.md §11.4c`）。

### 7.2 盒子来源优先级

来源：`core/pockets.py:867`（`select_site`）、`README.md §11.1`。

| 优先级 | 来源 | 说明 | `chosen_by` |
|:---|:---|:---|:---|
| 1 | **用户显式指定** | 表单中心/尺寸、指令里的坐标，或口袋分析 Agent 提交的盒子 | `request` / `pocket_agent` |
| 2 | **实验位点** | 注册表标注的已知位点，或用户上传受体里共晶配体的质心 | `experimental_site` |
| 3 | **P2Rank 预测** | 成熟的口袋预测工具 | `pocket_prediction` |
| 4 | **内置几何法** | 无外部依赖的兜底 | `pocket_prediction` |
| 5 | **蛋白质心** | 以上都不可用时的最后兜底，`box_source` 明确标注「不可靠」 | `centroid` |

**决策规则**（`core/pockets.py:918-963`）：

- 有**实验位点**时：以实验位点为准，同时用工具预测做**独立验证** ——
  一致（中心相距 ≤ `DEFAULT_AGREE_RADIUS = 8.0 Å`，`core/pockets.py:46`）就写进溯源；
  **不一致则记录警告**并写入 `box_warnings`；
- 只有**低可信兜底位点**（蛋白质心，`trust != "experimental"`）时：**改用工具预测的 top 口袋**；
- 完全没有参考位点时：直接用工具预测的 top 口袋；
- 工具不可用则逐级回退，并把「实际使用的来源」如实写进 `box_source`。

**盒子尺寸公式**：`size_i = clamp(口袋 extent_i + 2 × padding, min_size, max_size)`，
默认 `padding = 4 Å`、`min_size = 18 Å`、`max_size = 30 Å`（`core/pockets.py:47-49`、`settings.py:185-190`）；
Vina 网格间距 0.375 Å（`docs/architecture.md §15.7b`）。

### 7.3 库级配体下限（C 方案 B1）

来源：`core/pockets.py:252`（`library_span_bound`）、`settings.py:191-198`、`docs/api.md §13.5`。

| 项 | 规则 | 默认值 |
|:---|:---|:---|
| 开关 | `BOX_SPAN_ENABLED`；off = 旧行为（纯口袋驱动） | **on** |

| 下限公式 | `lib_lower_bound = max(POCKET_MIN_SIZE, round(P95 + 10, 1))`，其中 `+10 Å = 2×5 Å` | — |
| 与盒子的关系 | `size_i = clamp(pocket_extent_i + 2×padding, lib_lower_bound, max_size)` | — |
| 缓存 | 按库 SMILES 的 sha1 前 12 位缓存到 `assets/cache/box_span/`；缓存**只存 P95**，下限按当前 `min_size` 重算 | `core/pockets.py:283-297` |

### 7.7 换盒子实测：分数最大差 1.34 kcal/mol（原样引用）

来源：`docs/architecture.md §15.7b` 的 B0 表。
**参数**：2026-09-14，vina 1.2.7，凝血酶 1DWC 实验位点中心 `31.5/13.74/24.36`，
`exhaustiveness=4, n_poses=1, seed=42, threads=8`；格式 `分数 kcal/mol / 耗时 s`。

| 配体（3D 跨度 max Å） | 18³ | 22³ | 28³ | 34³ |
|:---|:---|:---|:---|:---|
| 乙醇（2.4） | −2.83 / 0.5 | −2.81 / 0.6 | −2.81 / 1.0 | −2.85 / 1.5 |
| 阿司匹林（5.4） | −5.87 / 0.8 | −5.87 / 1.0 | −5.86 / 1.3 | −5.88 / 1.8 |
| 华法林（8.4） | **−7.97** / 1.4 | −7.75 / 1.6 | −7.75 / 1.9 | −7.75 / 2.5 |
| 三肽模拟（10.0） | −8.55 / 4.9 | −7.47 / 4.9 | **−8.81** / 6.1 | −7.60 / 5.9 |
| 六肽（16.3） | −7.27 / 12.6 | −7.88 / 11.5 | −8.08 / 12.6 | **−8.21** / 12.8 |

**结论（照录）**：① 分数对盒子大小**敏感且非单调**（三肽模拟 18³→22³ 反而差 1.08），
所以「每个配体各自一个盒子」会直接把盒子效应混进排序；② 小分子耗时随盒子体积增长（0.5→1.5 s，约 3×），
而柔性大配体的耗时主要由可旋转键决定（12.6→12.8 s 几乎不变）；③ 大配体在 22³ 下确实被欠采样
（六肽 22³ −7.88 vs 34³ −8.21），因此需要「库级下限 + 超限分子分组」而不是逐分子自适应。

**最大差值**：同一配体在四个盒子下的最大分差 = 三肽模拟的 `|−8.81 − (−7.47)| = 1.34 kcal/mol`。

## 8. 对接计算与参数自动规划（重点）

**结论：Vina 调用链固定为「建受体 → 建网格图一次 → 逐配体设配体/dock/取能量」；
参数由 `core/params.py` 自动规划（精度优先），pilot 护栏保证不超时；
并发按分子数自动规划进程 × 线程，并对内存与可复现性都有护栏。**

### 8.1 Vina 1.2.7 调用链

来源：`core/docking.py:142`（`DockingSession`）、`core/docking.py:214`（`_dock_vina`）。

```
__init__: Vina(seed=42) → set_receptor(spec["pdbqt"]) → compute_vina_maps(center, box_size)  # 网格图只算一次，整批复用
dock():   describe_ligand(smiles) → smiles_to_pdbqt(seed) → set_ligand_from_string(pdbqt)
          → v.dock(exhaustiveness, n_poses) → best = v.energies(n_poses)[0]   # [total, inter, intra, torsional]
          → n_poses>1: v.write_poses(energy_range=3.0) / n_poses==1: v.write_pose(...)
```

| 能量项 | 结果字段 | 来源 |
|:---|:---|:---|
| 总结合亲和力 / 分子间 / 分子内 / 扭转惩罚 | `affinity_kcal_mol` / `intermolecular_kcal_mol` / `intramolecular_kcal_mol` / `torsion_kcal_mol` | `best[0..3]`，总分为 `round(..., 2)`（`core/docking.py:255-258`） |

- **网格图复用**：`compute_vina_maps` 与对接本身同量级开销，每个 worker 对「受体 + 盒子」**只算一次**（`README.md §4`）。
- **位姿语义**：`n_poses > 1` 必须真的写出全部位姿（`pose_count`），不能只写最优一个 —— 历史 bug（`core/docking.py:228-232`）。
- **盒子适配告警**：`span_i + BOX_GROUP_MARGIN > box_i` 时写 `box_fit_warning`，口径与分组判据一致（`core/docking.py:245-251`）。

来源：`core/params.py:383-485`。

| 项 | 规则 | 默认 / 位置 |
|:---|:---|:---|
| 触发 | 库 ≥ `AUTO_PARAM_PILOT_MIN`，且注入了 pilot 回调，且 `AUTO_PARAM_PILOT=on`，且用户未显式指定参数 | 50 |

### 8.6 并发规划表（`plan_concurrency`）

来源：`core/docking.py:86`（`plan_concurrency`）、`README.md §11.4b`。

| 分子数 | 进程 × 线程 | 理由 |
|:---|:---|:---|
| 1 | 1 × min(可用核, `DOCKING_SERIAL_THREADS`) | 单分子把核压在搜索上 |
| 1–7 | **1 × 8**（默认） | 少量分子用线程吃满核，避免多进程各自建图的固定开销 |
| 8 | `min(可用核, 24)` × `max(1, min(thread_cap, 可用核/workers))` | 进程与线程混合 |
| ≥ 50 | **最多 24 × 1** | 大库靠进程并行；受 `DOCKING_WORKERS` 与内存护栏约束 |

- 可用核 = `CPU 数 − 1`（留一核给主进程/服务，`core/docking.py:68`）。
- `thread_cap = min(DOCKING_SERIAL_THREADS, 16)`，默认 8（`core/docking.py:101`）。
- `DOCKING_WORKERS` 显式给出时覆盖自动规划，但仍被 `min(total, 内存上限)` 夹紧（`core/docking.py:104-109`）。
- **实测对照**（`README.md §11.4b`）：7 分子精算 **40.0 s → 8.1 s（4.9×）**。
- **实测并发（本次 e2e）**：单分子库的 note 为「对接并发：1 进程 × 8 线程」
  （`var/runs/20260915-174954-6983/run.json` 的 `notes`）。
- **实测并发（大库）**：96 分子 `exhaustiveness=1`，串行 **159.8 s** → 8 进程 **28.2 s（5.7×）**，结果**逐位一致**
  （`README.md §4`）。

### 8.7 内存护栏、LPT 调度与取消

| 项 | 内容 | 位置 |
|:---|:---|:---|
| **内存护栏** | `per_mb = max(64, DOCKING_WORKER_MEM_MB)`（默认 400 MB）；`cap = max(1, int(MemAvailable_MB × 0.7) // per_mb)`（留 30% 余量）；读不到 `/proc/meminfo` 时返回保守值 **64**；`per_mb` 下限 64 防除零 | `core/docking.py:72-83`、在 `plan_concurrency` 里与分子数/可用核一起夹紧（`core/docking.py:109`） |

| 已知缺口 | Agent 模式的 `cancel_event` 未传入对接工具（P0，见 §11.4 第 4.1 条） | `docs/architecture.md §15.4` |

### 8.8 可复现性（seed / seed_policy 与「批次无关」实测）

来源：`core/docking.py:142-162`、`docs/architecture.md §8.2`。

| 项 | 内容 |
|:---|:---|
| 默认种子 | `seed = 42`；结果行带 `seed` 与 `seed_policy="session"` |
| `seed_policy` 语义 | 只有 `"session"` 一种：Vina 每次 `dock()` 都按构造时的种子重新开始采样，因此**不需要也没有** per-molecule 的收益（`core/docking.py:160-162`） |
| **批次无关性** | 同一分子的分数与批次组成、提交顺序、进程数/分片方式**无关** —— 有永久回归测试 `tests/test_agent_context.py::test_scores_are_independent_of_batch_and_workers`（8 分子并行批里某分子的分数 == 它单独对接的分数，整批重跑也逐位一致） |
| 已验证并否决的做法 | **不要**为了「隔离」给每个分子换种子：那样只会改变分数而不带来收益（`docs/architecture.md §8.2`） |
| 独立复算取证 | `verify_docking.py` B 层用 `vina` API 从零重写对接，与工具输出**逐位一致**；配体 PDBQT sha256 相同；位姿用全新实例重打分一致（`README.md §13`） |
| 参数敏感性实测 | `exhaustiveness ∈ {1, 3, 6, 16}` → 分数 `{1: −5.84, 3: −5.87, 6: −5.78, 16: −5.85}`，极差 0.09 kcal/mol（本次实跑 `verify_docking.py` C3 层） |
| 能量恒等式 | `total = intermolecular + torsional` 对全部 8 分子成立（最大偏差 0.01，`README.md §13` C 层） |

> **注意**：不同搜索强度会得到不同分数（如 −5.78 @6 vs −5.87 @3），这是**参数真实参与计算**的表现，
> 因此排序 CSV 与 `docking.json` 都带 `engine` / `exhaustiveness` / `seed` / `seed_policy` 四列
> （`README.md §12`）。

## 11. 可信度、局限与风险

**结论：计算链路与「准备/对接/评估/报告」四段是真实且有测试看护的；
「主管协调」「自动异常处理」「结果可信度」三段目前主要是提示词纪律 + 工具事实上报，

### 11.1 打分函数与方法的固有边界

| 局限 | 说明 | 证据 |
|:---|:---|:---|
| Vina 打分函数是**近似** | 系统只编排引擎、不自研打分；分数高低是同一打分函数下的相对量，不等同实验亲和力 | `§1.2`、`§15.3` 第 3.2 条 |
| 受体质子化态（已实现，v0.23 起；v0.32 修复解析缺陷） | `pdb2pqr --ph-calc-method=propka --with-ph=<pH>` + meeko 按目标 pH 准备受体，逐残基 pKa/HIS 状态留痕。**v0.32 修复**：pdb2pqr 固定列下 4 位残基号（`GLU A1005`）会让 meeko 把 x 坐标当残基号（`int('128.990')`）导致四档全败并静默回退；现按「最后 5 个 token = x y z charge radius」反推残基键，`opt` 首档即成功 | `core/receptor_ph.py`、`tests/test_receptor_ph_parsing.py` |
| 结构水全部剔除；缺失残基/loop、点突变、二硫键、金属配位几何**只检测不建模** | 无法保留桥接水/配位水；断链口袋变形时结论不可用 | `§15.1` 第 1.8 / 1.2 条（**不建议**做建模，`§15.8` 第 1 条） |
| 配体互变异构/质子化态：**微观态已在目标 pH 窗口内枚举，但只取一个形式对接**；单一 3D 构象；立体化学只告警不处理 | Dimorphite-DL 给出窗口内多个微观态后按固定规则取一个（未做布居/能量比较）；柔性分子可能落在差的局部极小 → 假阴性；手性药物对接的是随机对映体 | `§15.1` 第 1.3 / 1.4 / 1.5 条（1.3 部分完成） |
| 无重打分 / 共识打分 / 位姿 RMSD / 聚类 | 单一 Vina 分直接决定结论，**无不确定性度量** | `§15.3` 第 3.2 条（P0） |
| 无相互作用指纹 / 接触图 / 残基能量分解；无富集/显著性（ROC/AUC/EF/p）；ADMET 仅 Lipinski；无阴性对照/诱饵集 | 无法解释盐桥/氢键网络；无法判断「优于对照」是信号还是噪声；类药性判断偏窄；无法估计假阳性率 | `§15.3` 第 3.3 / 3.4 / 3.5 / 3.6 条 |
| PAINS / 反应性基团 / 聚集剂过滤**全缺** | 榜单头部可能是泛检测干扰物 → 湿实验浪费（RDKit `FilterCatalog` 已带目录，成本极低） | `§15.3` 第 3.1 条（**P0 + S**） |

> 上表「证据」列的 `§` 均指 `docs/architecture.md`。

### 11.1b 质子化引擎（v0.32 起：受体与配体都用专业工具）

受体与配体按**同一目标 pH** 处理；两侧各用专业工具，且在报告与产物里逐条留痕：

| 侧 | 引擎 | 版本溯源 | 回退 |
|:---|:---|:---|:---|
| 受体 | `pdb2pqr`（`--ph-calc-method=propka`，即 **PROPKA** 逐残基 pKa）→ PQR → meeko PDBQT | 运行记录 `receptor_protonation.tool` / `pdb2pqr_version`、PROPKA 摘要随产物交付 | 找不到 pdb2pqr / 需保留有机辅因子 → 回退标准模板准备并标 `applied=false` + 原因 |
| 配体 | **Dimorphite-DL**（RDKit pKa 规则库），`LIGAND_PKA_ENGINE=auto` 默认 | `ligand_facts.protonation.engine` / `engine_version`；报告 §1.3 显示「质子化引擎：dimorphite-dl 2.0.2（N 个分子）」 | 未安装/异常 → 回退内置 pKa 规则表（近似），记 `engine_fallback_reason` + 安装提示 |

- **多微观态的取舍**：Dimorphite 在 pH 窗口（`LIGAND_PKA_WINDOW`，默认 ±0.5）内会返回多个
  微观态且不给布居数；系统按「`|净电荷|` 最小 → 带电原子最少 → 字典序」取**一个**形式对接，
  **全部候选与规则**写进 `ligand_facts.protonation.variants` / `variant_rule`，报告 §6 同步声明
  「未做布居与能量比较」。需要逐态枚举时用 SDF 提供已准备形式并选 `keep`。
- **安装（重要）**：Dimorphite-DL 2.0.2 的元数据把 `rdkit` 钉在 `<2026`，而本项目要求
  `rdkit>=2026.3.6`；直接安装会**降级 RDKit**。用 `--no-deps` 安装（实测 2.0.2 与 2026.3.6 兼容）：

      uv pip install loguru && uv pip install --no-deps dimorphite-dl

  `uv pip check` 会因此报一条**预期内**的 `dimorphite-dl requires rdkit<2026` 提示，可忽略。
- **探测**：`bash scripts/doctor.sh`、`POST /api/tools/probe`（字段 `pka`）、设置页「检测」三处同源。

实现上这 6 层由 `runtime/llm.py:140-154`（`_layers`）按**从低到高**顺序叠加，

**运行类字段**：`界面设置 > .env > 内置默认`（`settings.py:20-23`）。

回滚时只删自己注入的键（历史 bug：`reset` 误删 shell/CI 注入的变量）。

**只读（部署保护）项**：`PORT`、`DOCKING_MAX_LIGANDS`、`UPLOAD_MAX_MB`
（`settings.py:317-326`，`env_priority=True`）—— `.env` 优先，界面只读；
`reject_readonly()` 会**整包拒绝**提交（前端也已跳过只读字段，双重保护）。

**需要重启的项**：`CHECKPOINT_BACKEND`（`settings.py:310`）、`ARTIFACT_BASE_URL`（`settings.py:312`）
（`needs_restart=True`）。其余保存后在新的运行里立即生效。

**密钥三条约定**（`README.md §2.1`）：`LLM_API_KEY` 与各角色 `api_key` **只写不读**（界面只显示「已配置 + 首尾 4 位掩码」）；

上游失败的错误信息**脱敏**（`sk-…`、`Bearer …` 等被替换）。

**设置文件**：`config/local_settings.json`（已 gitignore 与打包排除）；不存在时行为与之前完全一致；

### 15.3 术语表

| 术语 | 含义 |
|:---|:---|
| **Vina** | AutoDock Vina，本系统的主对接引擎（1.2.7），提供打分函数与采样；结果为近似结合自由能（kcal/mol），越负表示越强 |
| **AutoDock4（AD4）** | 经典 AutoDock4 CPU 引擎（`autodock4`/`autogrid4`），作为 Vina 不可用时的回退；其分数与原引擎**不可通约** |
| **PDBQT** | AutoDock 系列的受体/配体输入格式，在 PDB 基础上增加原子类型、电荷与可旋转键（TORSDOF）信息 |
| **HETATM** | PDB 中非标准残基记录（金属离子、辅因子、水、共晶配体、结晶添加剂等） |
| **apo** | 不含辅因子/共晶配体的受体结构；本系统在丢弃杂原子时会在报告中标明结论是「去辅因子（apo）条件下的结果」 |
| **apex / 药效团锚定基团** | 与靶点关键亚口袋（如丝氨酸蛋白酶 S1 口袋）形成特征性相互作用的官能团，本系统用 SMARTS 匹配脒基/胍基/羧酸/磺酰胺/芳环 |
| **funnel（两阶段漏斗）** | 大库打法：先全库低强度粗筛，再对头部高强度精算；合并时精度优先，粗筛分保留在 `affinity_coarse` |
| **pass（阶段）** | 漏斗的一轮（`coarse` / `fine`）；**同一 pass 内参数与盒子完全一致** |
| **shard（分片）** | 把分子库切成多片分别调度；本系统**不推荐**（LLM 往返开销），且片数受 `AGENT_SHARD_MAX=8` 约束 |
| **box_group** | 对接盒分组：`main`（主组，全库共用主盒）与 `large`（超限大配体，同一中心的更大盒子）；**不跨组比较分数** |
| **pocket（口袋）** | 受体表面可能结合小分子的空腔；由 P2Rank（机器学习）或内置几何法预测，或由共晶配体/注册表给出实验位点 |
| **candidate（候选）** | ① 候选分子（待筛选的小分子）；② 候选口袋；③ 在线解析时的候选受体条目（accession 级）。上下文会明确是哪一种 |
| **task_spec（任务规约）** | 受理层产出的结构化任务描述，含 `decision`/`authority`/`receptor`/`ligands`/`site`/`params` 等只读字段 |
| **decision** | `run` / `ask` / `reject` 三态，是受理层对「该跑还是该问」的显式判定，编排层无条件服从 |
| **blackboard（共享黑板）** | 运行级进程内共享工作区，子 Agent 通过它横向交换分子/性质/口袋/位点/对接/结合模式 |
| **tool_io 视图** | 工具原始返回全量落盘，只把 summary + top-N 回给模型；`AGENT_TOOL_TOP_N` 只控制视图大小 |
| **choices** | 解析出现多个候选或置信度不足时下发的结构化选项（前端渲染成按钮），点选后以同一 `conversation_id` 继续 |
| **unresolved** | 点名受体在线解析失败/歧义时写回的 `receptor.source`；此时 `run_docking` 代码级护栏**在调用任何引擎前**拦下 |
| **param_plan** | 参数自动规划的可追溯产物：`exhaustiveness`/`n_poses`/漏斗/pilot/每条决策理由 |
| **pilot** | 预算护栏的探针：用最贵的少数分子以 `exhaustiveness=1` 真实试跑并外推总耗时；**只测量**，不写位姿、不进排序 |
| **completeness** | 运行记录里「本次实际完成了什么」的字段；**仅信息展示，不驱动行为**（服务端不事后接管/不自动补齐） |
| **seed_policy** | 种子策略；当前只有 `session`（Vina 每次 `dock()` 按构造种子重新采样，故分数与批次无关） |
| **内容寻址缓存** | 以「源文件内容哈希 + 影响结果的参数哈希」为键的缓存（而非时间戳），避免并发互相覆盖与缓存恒失效 |
| **LPT 调度** | Longest Processing Time first：按成本（可旋转键×4 + 重原子）从大到小提交对接，减少尾部拖尾 |
| **P95（最近秩法）** | 百分位取法：`vals[min(rank, n)-1]`，n≤20 时即最大值；用于库级跨度下限，抗单个异常值 |
| **C 方案** | 对接盒的「库级配体感知下限 + 超限分子分组」实现（`docs/architecture.md §15.7b`） |
| **门禁** | 改完代码必须全绿的可执行检查集合（pytest / smoke / verify_docking / check_web / snapshot_ids / ui_e2e / ui_shot / intake_eval / lint_local） |
| **取证（反证控制）** | 不信任自身封装的验证方法：独立复算 + 「参数一变结果必须变」的反向证明 |

**报告结束。** 本报告的全部数值均来自仓库内代码、既有文档与本次实测运行；
未实测的量已明确标注为「未实测」，未做任何推算冒充实测。
